# Deploying to Render

The second supported topology. The first is docker-compose on a VPS behind
nginx — see [DEPLOYMENT.md](DEPLOYMENT.md). Pick one per environment.

`render.yaml` at the repository root is the blueprint: managed Postgres, a Key
Value instance, and the four applications as separate services.

## Read this before applying the blueprint

**The API will not start until every secret below exists.** With
`NODE_ENV=production` the environment contract validates configuration before
anything else runs and exits 78 (`EX_CONFIG`) rather than boot on an unsafe
default. It refuses:

| Refused                          | Because                                                        |
| -------------------------------- | -------------------------------------------------------------- |
| `PAYMENT_PROVIDER=mock`          | A storefront taking real orders on a fake payment adapter       |
| Stripe with no webhook secret    | An unverified webhook is an open endpoint that marks orders paid |
| `EMAIL_PROVIDER=console`         | Confirmations and password resets would silently go nowhere     |
| `STORAGE_PROVIDER=filesystem`    | Instance disk does not survive a restart and is not backed up   |
| `FULFILLMENT_PROVIDER=mock`      | Orders that are never actually shipped                          |
| `AI_PROVIDER=development`        | Stand-in output presented as a model's                          |
| An `http://` public URL          | Cookies and tokens over plaintext                               |
| A wildcard or empty CORS list    | Any origin able to drive an authenticated session               |
| Key material under 32 bytes      | Forgeable tokens                                                |
| `COOKIE_SECURE=false`            | Session cookies sent in the clear                               |

A crash loop on first apply is these guard rails working. `node
scripts/verify-production-guards.mjs` asserts them in CI, so none of them can
be quietly removed to get a deploy green.

## What you need before you start

Nothing here can be generated by this repository. Each is an account you open
and a credential you paste into Render when it prompts.

| Secret                                     | Where it comes from                                         |
| ------------------------------------------ | ----------------------------------------------------------- |
| `PAYMENT_SECRET_KEY`, `PAYMENT_WEBHOOK_SECRET` | Stripe dashboard. The webhook secret comes from the endpoint you register at `<API_PUBLIC_URL>/api/v1/webhooks/stripe` |
| `EMAIL_API_KEY`, `EMAIL_FROM`               | Resend, SES or SMTP. The sending domain needs SPF and DKIM before anything lands in an inbox |
| `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` | An S3 bucket with a least-privilege IAM user. Not public-read; media is served through `MEDIA_PUBLIC_BASE_URL` |
| `THREEPL_API_KEY`, `THREEPL_API_SECRET`     | ShipBob, once a 3PL contract exists                         |
| `SESSION_SECRET`, `ENCRYPTION_KEY`          | `openssl rand -base64 32` — generate two different values   |
| `SENTRY_DSN`                                | Sentry project, optional                                    |

`ENCRYPTION_KEY` protects TOTP secrets at rest. Rotating it without a
re-encryption pass locks every staff member out of MFA, so treat it as
permanent until there is a runbook entry for rotating it.

AI can stay `disabled`, which is a fully supported production configuration.

## Order of operations

The public URLs are circular — the API needs to know the storefront's origin
for CORS, and the storefront needs the API's address — and neither is known
until Render has assigned hostnames. So it is two passes.

1. **Apply the blueprint.** Render creates the database, the Key Value
   instance and the four services, and prompts for every `sync: false` value.
   Supply the secrets you have; use placeholder `https://` URLs for the four
   address variables for now.
2. **Let the first deploy fail.** It will: the addresses are wrong. This is
   expected.
3. **Collect the assigned hostnames** from the Render dashboard, or attach
   custom domains now if you have them — doing it now avoids a third pass.
4. **Set the real addresses** on the API and worker: `API_PUBLIC_URL`,
   `STOREFRONT_PUBLIC_URL`, `ADMIN_PUBLIC_URL`, and `CORS_ALLOWED_ORIGINS`
   listing the storefront and admin origins explicitly. On the storefront and
   admin: `API_INTERNAL_URL`, `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_ADMIN_URL`.
5. **Register the Stripe webhook** at `<API_PUBLIC_URL>/api/v1/webhooks/stripe`
   and set `PAYMENT_WEBHOOK_SECRET` from it.
6. **Redeploy.** The API's pre-deploy step applies migrations; `/health/ready`
   goes green once the database and Key Value are both reachable.
7. **Seed RBAC.** `pnpm --filter @health/database run seed:rbac` from a one-off
   job. This creates the role and permission catalogue only — not demo
   products, not demo customers.
8. **Create the first administrator** and enrol MFA immediately. Privileged
   roles cannot operate on a single factor; the grace period is bounded by the
   `security.staff_mfa_grace_period_days` setting.
9. **Lock down the admin console.** Replace the empty `ipAllowList` on
   `health-commerce-admin` with your office or VPN CIDRs. This is where claims
   are approved, refunds issued and recalls authorised.
10. **Turn on indexing** — `NEXT_PUBLIC_ALLOW_INDEXING=true` on the storefront
    — only when the real launch is intended. It is off by default so a staging
    copy cannot get itself indexed as a second storefront selling regulated
    products.

## What Render does not give you

Render's managed Postgres has its own backups. That is not the same as the
encrypted, off-platform backups `scripts/backup.sh` produces, and it is not a
disaster recovery plan:

- **`scripts/backup.sh` and `scripts/restore.sh` assume docker-compose.** They
  call `docker compose exec postgres`. On Render they need rewriting against
  the external connection string before they will run at all.
- **A backup you have never restored is not a backup.** No restore drill has
  been run against this platform, on any topology.
- **Nothing alerts on backup freshness.** The failure mode is silence until the
  day you need a restore.

The monitoring stack in `infrastructure/monitoring/` (Prometheus, Grafana,
Alertmanager) is also compose-shaped. On Render you either run it elsewhere and
scrape the services, or use Render's own metrics and lose the alert rules. The
rules encode real operational knowledge — refresh token reuse, audit write
failure, outbox backlog — so dropping them silently is a downgrade worth
deciding on deliberately rather than discovering.

## Before you call this production

Phase 8 is production hardening and it is **not complete**. See
[../architecture/ROADMAP.md](../architecture/ROADMAP.md). Outstanding:

- No load testing. No throughput or concurrency figure is claimed anywhere in
  this repository, and none should be quoted until Phase 8 measures it — which
  means the instance sizes in `render.yaml` are a starting guess, not a sizing.
- No penetration test by an independent party.
- No browser end-to-end tests.
- No backup *and restore* drill.
- The security regression suite in `apps/api/test/security.e2e-spec.ts` has
  never been executed.

None of that stops a deploy. All of it should stop a launch that takes real
money from real customers buying regulated health products.

## Cost

The blueprint specifies paid plans throughout, deliberately. Free Postgres on
Render is deleted after 30 days and has no point-in-time recovery, and free web
services sleep when idle — a storefront that cold-starts on the first customer
of the morning, and a database that vanishes a month after launch. Neither is
compatible with the recovery expectations in this repository's own
documentation.
